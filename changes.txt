Change H: Relative and absolute time values
In the alarm-set add a property, if the alarm-events are defined by absolute or relative time values.
If the switch is set to "absolute time values", it behaves as right now: Each alarm-set has a given time of day, when the alarm-event shall trigger.
If the switch is set to "relative time values", then the alarm-set shall have a "end time" as time of the day. The individual alarm-events then have configured a relative time offset to the "end time" of the alarm-set. E.g. "end time" in alarm-set is "8:00", the time offset is "10 min" in the alarm-event. Then it shall trigger at "7:50".

Q3. Accepted devices storage: How should accepted BT devices be stored in DataStore?

  Option A — Store MAC addresses only (List<String>):
    DataStore holds e.g. ["AA:BB:CC:DD:EE:01", "AA:BB:CC:DD:EE:02"]
    The display name in the multi-select UI is resolved live from BluetoothAdapter.bondedDevices at the time the screen is opened.
    Pro: Simple, small storage, always reflects current device names (name changes on device show up automatically).
    Con: If a device is later unpaired (removed from the phone's BT settings), its MAC is still in the DataStore list
         but it won't appear in the UI's "paired devices" multiselect anymore — it becomes a "ghost" entry.
         The check still works correctly (no connected device matches the MAC → notification fires), but the
         user cannot see or remove the ghost entry from the UI unless the device is re-paired.
    Example stored value:
      acceptedDevices: ["AA:BB:CC:DD:EE:01", "AA:BB:CC:DD:EE:02"]
    Example UI (resolved at screen-open time):
      [✓] JBL Clip 4          (AA:BB:CC:DD:EE:01)
      [✓] Sony WH-1000XM5     (AA:BB:CC:DD:EE:02)
      [ ] AirPods Pro         (FF:EE:DD:CC:BB:03)

  Option B — Store MAC + name pairs (List<{mac, name}>):
    DataStore holds e.g. [{"mac":"AA:BB:CC:DD:EE:01","name":"JBL Clip 4"}, ...]
    The multi-select UI shows saved names for already-selected devices, and live names for newly paired ones.
    Pro: Ghost entries remain visible (and removable) in the UI even after unpairing.
         The user can see "JBL Clip 4 (nicht mehr gekoppelt)" and explicitly remove it.
    Con: Slightly more complex storage; name in DataStore can drift out of sync if the user renames the BT device.
    Example stored value:
      acceptedDevices: [{"mac":"AA:BB:CC:DD:EE:01","name":"JBL Clip 4"}, {"mac":"AA:BB:CC:DD:EE:02","name":"Sony WH-1000XM5"}]
    Example UI:
      [✓] JBL Clip 4          (AA:BB:CC:DD:EE:01) ← from DataStore, still paired
      [✓] Sony WH-1000XM5     (AA:BB:CC:DD:EE:02) ← from DataStore, still paired
      [ ] AirPods Pro         (FF:EE:DD:CC:BB:03) ← from live bondedDevices, not yet selected
      --- not currently paired ---
      [✓] Old Headset         (11:22:33:44:55:66) ← from DataStore only, already unpaired → shown as ghost, user can deselect

  => PROPOSED: Option B — storing name + MAC is more user-friendly because ghosts stay manageable.
     The connectivity check at alarm time always uses the MAC only (ignoring the stored name), so correctness is unaffected.
  --> Option B.
